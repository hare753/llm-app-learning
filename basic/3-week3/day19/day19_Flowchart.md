## 二、第 1 步：`test_validation_directly()` 流程图（不花 API）

```text
开始
  │
  ▼
┌─────────────────────────────────────┐
│ cases = [                           │
│   ("加法正常",   lambda: calc(1,2,"+")), │  ← 定义时不执行
│   ("除零错误",   lambda: calc(100,0,"/")),│
│   ... 共 12 个                       │
│ ]                                   │
└─────────────────────────────────────┘
  │
  ▼
for name, fn in cases:  ─────────┐
  │                              │
  ▼                              │
┌───────────────────────┐        │
│ result = fn()         │        │
│  ↑                    │        │
│  └─ 现在才执行 lambda  │        │
│     → calculator(...)  │        │
│     → 校验 → 返回字符串 │        │
└───────────────────────┘        │
  │                              │
  ▼                              │
print("[直接校验] xxx → 结果")    │
  │                              │
  └──── 循环 12 次 ───────────────┘
  │
  ▼
结束（全程本地，0 次网络调用）
```

**核心理解**：`lambda: calculator(1, 2, "+")` 只是"打包了一个还没执行的调用"。`fn()` 时才真正执行。这就是为什么 `cases` 定义时不会立刻算 12 次。

## 三、第 2 步：`run_with_tools()` 完整 FC 流程图

这是整个 Day19 的主流程图，也是所有 Agent 的底层原理。

```text
开始 run_with_tools("帮我算 100 除以 0 等于多少？")
  │
  ▼
┌──────────────────────────────────────────────┐
│ messages = [                                 │
│   {"role":"system", "content": SYSTEM_PROMPT},│
│   {"role":"user",   "content": user_query},  │
│ ]                                            │
└──────────────────────────────────────────────┘
  │
  ▼
╔══════════════════════════════════════════════════╗
║ 【第一次调用】模型决策                            ║
║   resp = client.chat.completions.create(          ║
║       model, messages, tools=tools, temp=0)       ║
║                                                   ║
║   模型读 tools 里的 description → 决定：           ║
║     调不调？调哪个？传什么参？                     ║
╚══════════════════════════════════════════════════╝
  │
  ▼
assistant_msg = resp.choices[0].message
messages.append(assistant_msg)   ← 关键！不加会报错
  │
  ▼
assistant_msg.tool_calls 是否为空？
  │
  ├── 空 ──► [模型回答] 未选工具，直接回答 ──► 结束
  │
  └── 非空
        │
        ▼
     for tool_call in assistant_msg.tool_calls:  ─────┐
        │                                              │
        ▼                                              │
     ┌──────────────────────────────────────┐         │
     │ _execute_tool(                        │         │
     │   tool_name = tool_call.function.name,│         │
     │   raw_args  = tool_call.function.arguments,│    │
     │   tool_call_id = tool_call.id,        │         │
     │   messages                            │         │
     │ )                                     │         │
     └──────────────────────────────────────┘         │
        │                                              │
        │  展开 _execute_tool：                        │
        │  ┌────────────────────────────────┐          │
        │  │ ① json.loads(raw_args)         │          │
        │  │    字符串 → Python dict         │          │
        │  │    失败 → 错误字符串 → 回传      │          │
        │  │                                │          │
        │  │ ② func = TOOL_MAP.get(name)    │          │
        │  │    找不到 → "未知工具" → 回传    │          │
        │  │                                │          │
        │  │ ③ result = func(**args)         │          │
        │  │    ** 把 dict 拆成关键字参数     │          │
        │  │    工具内部已校验，返回字符串     │          │
        │  │    （成功=结果，失败=错误信息）  │          │
        │  │                                │          │
        │  │ ④ messages.append({            │          │
        │  │     "role":"tool",             │          │
        │  │     "tool_call_id": id,        │          │
        │  │     "content": result_str,     │          │
        │  │   })                           │          │
        │  └────────────────────────────────┘          │
        │                                              │
        └──── 循环处理所有 tool_calls ─────────────────┘
        │
        ▼
     messages 现在 = [
        system,
        user,
        assistant (含 tool_calls),
        tool  (含工具结果或错误),
        tool  (可能多个),
     ]
        │
        ▼
╔══════════════════════════════════════════════════╗
║ 【第二次调用】模型组织自然语言                    ║
║   resp2 = client.chat.completions.create(         ║
║       model, messages, temp=0)                    ║
║                                                   ║
║   模型看到：用户问题 + 自己的决策 + 工具结果      ║
║   任务：把结果组织成人话                          ║
║         如果工具返回错误，就解释错误 + 给建议      ║
╚══════════════════════════════════════════════════╝
  │
  ▼
answer = resp2.choices[0].message.content
print("[模型回答]", answer)
  │
  ▼
return answer
  │
  ▼
结束
```

**核心理解**：**两次调用，各司其职。**
- 第一次：给模型 `tools`，让它做**决策**
- 第二次：给模型工具**结果**，让它做**总结**

## 四、第 3 步：`_test_error_recovery()` 流程图

这是"作弊"路径——不等模型犯错，我们**手动构造**模型的错误决策，直接进入错误处理环节。

```text
开始 _test_error_recovery(
    tool_name="calculator",
    args_json='{"a": 2, "b": 3, "operator": "^"}',
    user_question="请帮我算 2 的 3 次方。"
)
  │
  ▼
┌───────────────────────────────────────────────┐
│ messages = [                                  │
│   {"role":"system", "content": SYSTEM_PROMPT},│
│   {"role":"user",   "content": user_question},│
│   {                                           │
│     "role":"assistant",                       │
│     "content": None,                          │
│     "tool_calls": [                           │
│       {                                       │
│         "id": "call_test_1",                  │
│         "type": "function",                   │
│         "function": {                         │
│           "name": "calculator",               │
│           "arguments": args_json,  ← 我们手写的错误参数！│
│         }                                     │
│       }                                       │
│     ]                                         │
│   }                                           │
│ ]                                             │
└───────────────────────────────────────────────┘
  │
  ▼
_execute_tool(...)   ← 复用 Day19 核心执行逻辑
  │
  ├─ json.loads → {"a": 2, "b": 3, "operator": "^"}
  ├─ TOOL_MAP.get("calculator") → calculator 函数
  ├─ calculator(2, 3, "^")
  │     └─ operator "^" 不在 ("+","-","*","/") 里
  │         → return "参数错误：operator 只能取 ..."
  └─ messages.append({"role":"tool", "content":"参数错误：..."})
  │
  ▼
╔══════════════════════════════════════════════════╗
║ 【第二次调用】模型组织自然语言                    ║
║   模型看到"参数错误：..."                         ║
║   → 识别为失败                                    ║
║   → 向用户解释出错原因                            ║
║   → 给出修正建议                                  ║
╚══════════════════════════════════════════════════╝
  │
  ▼
print("[模型回答]", ...)
  │
  ▼
结束
```

**为什么需要这个函数**：模型很聪明，它看 `enum` 里写着 `["+","-","*","/"]`，多半不会主动传 `^`。正常 `run_with_tools()` 跑不出"非法 operator"场景，需要**手动构造 `assistant` 消息**才能稳定覆盖边界。

## 五、四层"决策 vs 执行"对照表

这是 Day19 最重要的逻辑认知。

```text
┌─────────────────────┬──────────────────────────────┬───────────────────┐
│ 环节                 │ 谁在做？                      │ 在哪里？           │
├─────────────────────┼──────────────────────────────┼───────────────────┤
│ 决定"调哪个工具"     │ 🤖 模型                       │ 第一次 API 调用     │
│ 决定"传什么参数"     │ 🤖 模型                       │ 第一次 API 调用     │
├─────────────────────┼──────────────────────────────┼───────────────────┤
│ 解析参数             │ 👤 你的 Python                │ _execute_tool     │
│ 校验参数（类型/枚举）│ 👤 你的 Python                │ calculator 内部   │
│ 真正执行运算         │ 👤 你的 Python                │ calculator 内部   │
├─────────────────────┼──────────────────────────────┼───────────────────┤
│ 把结果组织成自然语言 │ 🤖 模型                       │ 第二次 API 调用     │
│ 把错误解释给用户     │ 🤖 模型                       │ 第二次 API 调用     │
└─────────────────────┴──────────────────────────────┴───────────────────┘
```

**四步闭环口诀**：

```text
模型决策  →  本地校验  →  错误回传  →  模型总结
 (API)       (Python)     (messages)     (API)
```

**这就是所有 Agent 的底层原理**。不管以后用 LangChain、LangGraph 还是自己写，万变不离这四步。

## 六、数据形态演变图（关键！）

看数据怎么一步步变形。理解了这张图，就理解了 FC。

```text
用户输入：
  "帮我算 100 除以 0 等于多少？"           【Python str】

      ↓ messages = [{"role":"user", "content": ...}]

第一次 API 调用：
  请求发出去 → 返回 assistant_msg

      ↓

assistant_msg.tool_calls[0].function.arguments
  '{"a": 100, "b": 0, "operator": "/"}'   【JSON 字符串】

      ↓ json.loads(...)

  {"a": 100, "b": 0, "operator": "/"}     【Python dict】

      ↓ ** 解包

  calculator(a=100, b=0, operator="/")     【函数调用】

      ↓ 校验：除零命中

  "计算错误：除数不能为 0"                  【Python str】

      ↓ messages.append({"role":"tool", "content": ...})

第二次 API 调用：
  请求发出去 → 返回自然语言

      ↓

  "这次计算失败了，原因是除数不能为 0。..." 【Python str】
```

**关键点**：`arguments` 是 **JSON 字符串**（不是 dict），必须 `json.loads` 才能用。这是新手最容易搞混的地方。

## 七、你的观察完全正确：这是"设计流程"而非"写代码"

你说得对——Day19 的学习重点不在代码语法，而在**逻辑设计**。具体来说：

### 你在学的三件事（按重要性排序）

```text
优先级 1（最重要）：
  ├─ 流程设计：模型决策 → 本地校验 → 错误回传 → 模型总结
  ├─ 责任边界：模型做什么？Python 做什么？
  └─ 容错思维：错误不抛异常，包装成字符串回传

优先级 2（中等）：
  ├─ 数据结构：JSON 字符串 ↔ Python dict
  ├─ 契约设计：工具函数统一返回 str（成功/失败都用 str）
  └─ 消息流：messages 列表如何随时间演变

优先级 3（最次要）：
  ├─ 语法细节：f-string、lambda、isinstance
  └─ 边界 case：bool 是 int 子类等
```

**为什么优先级 1 最重要**：因为即使 AI 帮你写代码，**你必须先想清楚"谁做什么"**，AI 才能写对。你脑子里没有流程，AI 写出来你也没法判断对错。

### 学完 Day19 你应该能脱稿说清的事

不看代码，能口述：

1. **为什么需要两次 API 调用？** —— 第一次模型决策，第二次模型总结
2. **模型到底"执行"了什么？** —— 什么都没执行，只发了个调用请求
3. **参数从字符串到函数调用的过程？** —— JSON str → `json.loads` → dict → `**` 解包
4. **为什么错误要回传而不是抛异常？** —— 让模型组织自然语言解释，比程序崩掉体验好
5. **`tool_call_id` 是干什么的？** —— 把 `tool` 消息和模型的调用请求对上号
6. **为什么工具函数返回字符串而不是数字？** —— 统一契约，调用方不需要 try/except 判分支
7. **`_test_error_recovery` 为什么要手动构造？** —— 模型不会主动犯错，只能手动触发边界

### 面向 AI 提问的正确姿势

既然你走的是"设计流程 → 让 AI 写代码"的路径，提问模板应该是：

```text
❌ 不好的问法：
   "帮我写一个 Function Calling 代码"
   （AI 不知道你要什么结构）

✅ 好的问法：
   "我要实现这个流程：
    1. 用户提问 → 调 API 让模型选工具
    2. 本地执行工具，返回字符串（成功=结果，失败=错误信息）
    3. 把结果作为 role:'tool' 回传
    4. 再调 API 让模型组织自然语言
    请按这个流程写代码，工具函数内部做参数校验。"
```

**你先设计，AI 才写得出对的**。你的观察恰好点中了 FC 学习的关键：**它是一门"设计学"，不是"语法学"**。
